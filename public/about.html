Why This Site Exists

Most SQL problems are not performance problems. They are readability problems: a four-hundred-line statement pasted out of a log line, a migration file where three people used three different indentation styles, a query someone wrote six months ago that nobody wants to touch. Every database vendor ships a formatter inside its paid client and every editor has a plugin for it, but all of those assume you have the right client installed and permission to add extensions to a locked-down work machine. SQLFormat.io assumes none of that. Open a tab, paste the statement, read the result, close the tab.

The scope is deliberately narrow. The site formats, minifies, validates, escapes, and converts SQL. It does not connect to your database, keep a copy of your schema, or try to become a query IDE. That narrowness is what keeps the whole thing small enough to load instantly and to keep working from the browser cache after the first visit.

Who It Is Built For

The tool gets used most often by people who need a query readable right now, not after a tooling detour:

  • Backend engineers who pulled a statement out of an application log or an ORM and need to see its shape before debugging it.
  • Analysts who exported SQL from a BI tool and want to re-indent it before pasting it into a notebook or a ticket.
  • DBAs and on-call engineers triaging a production issue on a jump host where you can install nothing, but you can open a browser.
  • Students and interview candidates learning to read joins and subqueries without a database client at hand.
  • Technical writers and reviewers who need consistent, aligned SQL inside documentation, pull requests, and runbooks.

These are different jobs, but they share one constraint: the query is often sensitive and the environment is often restricted. That constraint shaped every design decision below.

Why Nothing Is Uploaded

Queries carry real data. A WHERE clause can contain customer emails, an INSERT can contain payment identifiers, and a schema dump leaks your entire data model. Pasting that into a server-side formatter means trusting a stranger's logging policy, and "we delete logs after 30 days" is not something you can verify. So the formatter runs as client-side JavaScript on your own machine. There is no fetch call, no WebSocket, and no backend endpoint that receives SQL; the tool is a static HTML page with a script tag, and the transformation happens in the same process as the tab you are looking at.

Two things do leave the browser, and it is worth being precise about which. Google Analytics records page views, so it knows that someone opened the formatter, not what was pasted into it. AdSense serves the ad slots. The query text itself never enters either request. The only persistence is the last five formatted queries saved to localStorage so you can recover a recent paste — that list lives in your browser profile, is visible in DevTools, and disappears when you clear the panels or clear site data. If you are on a shared or managed device, treat it exactly as you would a text file on that machine.

How the Formatting Actually Works

The formatter is a tokenizer plus a layout engine, not a full grammar-aware rewriter. The first pass scans the statement and classifies each token: keywords, identifiers, quoted identifiers, string literals, numeric literals, operators, and comments. Strings and quoted identifiers are held as opaque units, which is why a value like 'SELECT * FROM t' stays inside its quotes instead of being rearranged as code. The second pass re-emits the token stream with deterministic whitespace rules — major clauses (SELECT, FROM, WHERE, GROUP BY, ORDER BY, JOIN) start a new line, nested subqueries and CASE blocks indent by one level, and comma lists get one item per line once they pass a length threshold.

Because the token stream is only re-spaced and never reordered, formatting cannot change what a query means, and the minifier can reverse the operation without guessing. Where the approach has limits, we say so instead of hiding it: procedural blocks in PL/SQL and T-SQL, dynamic SQL assembled from string concatenation, and input with unbalanced quotes are passed through rather than mangled into something that merely looks valid.

-- Input (one line) select u.id,u.email,o.total from users u left join orders o on o.user_id=u.id where o.status='paid' order by o.total desc; -- Output SELECT u.id, u.email, o.total FROM users u LEFT JOIN orders o ON o.user_id = u.id WHERE o.status = 'paid' ORDER BY o.total DESC;

Dialect Support and Correctness

The dialect list is not decoration; each one changes how the tokenizer classifies text. Identifier quoting differs (`backticks` in MySQL, "double quotes" in standard SQL and PostgreSQL, [brackets] in T-SQL), so the wrong dialect can leave a quoted name looking like a syntax error. Comment syntax, string concatenation, and keyword sets differ as well, and the vendor-specific list continues from there: LIMIT versus TOP versus FETCH FIRST, JSON operators, and BigQuery's fully-qualified project.dataset.table names.

When output looks wrong, the fastest check is the syntax validator, which flags unbalanced parentheses and a list of common misspellings such as SELCET for SELECT and WHRE for WHERE. Beyond that, the honest rule is that a formatter is not a parser: if the output looks plausible but your database rejects it, the tokenizer classified something the way your engine would not, and that is a bug worth reporting.

How the Site Is Maintained

This is a small, single-maintainer project, and the changelog below is the record of it: every entry is dated and describes what changed, without marketing language. Guide pages are written to describe what the tools actually do, in the order someone would use them, and they are updated when behaviour changes rather than left to drift. When a dialect's handling changes, the page that documents it changes in the same pass.

That is also why the content is longer than a typical tool page. A page that only says "paste your SQL and click Format" is not useful to someone who is trying to decide whether a client-side formatter is safe for production data, or whether escaping a quote is a security fix (it is not — see the escape guide). Explaining the tradeoffs is part of the tool.

📬 Contact

Have feedback or suggestions? Feel free to contribute on GitHub.

A good bug report for a formatter has four things in it: the SQL you pasted (redact real values first, but keep the structure intact), the dialect you selected, what you expected the output to look like, and your browser and operating system. A short before/after excerpt is worth more than a paragraph of description, because the fix almost always starts with reproducing the exact token sequence that was misclassified.

Feature requests are read too, and the ones that get built fastest are the narrow ones — "add FETCH FIRST handling for DB2", "keep one-line CASE blocks on one line", "support a new dialect". If you are asking for a new dialect, include its identifier quoting rules and the keywords that differ from standard SQL; that is most of the work.

Set expectations accordingly: this is a side project maintained by one person, so replies are best-effort and there is no support SLA. Privacy questions about what the tools transmit are answered on the privacy page.
